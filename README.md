1. Why is hiding a React button not sufficient for RBAC?
Hiding a button in React only prevents users from viewing it on the interface. A malicious user can still send HTTP requests directly to the backend using online tools like Postman or by modifying the browser. To stop this the backend must verify the user's role and permissions before allowing any protected action.

2. Why does decoding a token not verify its authenticity?
Decoding a JWT simply reads information like the users email and roles, it does not prove the tokens authenticity like if the token was generated by the server or that it hasn't been modified. The Authenticity is only proven when the backend check the JWT signature using the secret key. Jwt (user token) + (server math formula) Secret key (JWT_SECRET) = JWT Signature.

3. Why must the backend check the organisation as well as the role name?
A user may have different roles in different organisations. For example, a person could be a manager in one organisation and a normal user in another. If the backend only checked the role name, a normal user could incorrectly manage polls belonging to another organisation. By checking both the role and the organisation ID, the backend ensures that users can only perform actions that they were given permission to.

4. Why must the administrator ignore the token returned when creating a manager?
When an administrator creates a manager account, the backend returns a JWT for the newly created manager. If the administrator saved this token, and they used this token then they would immediately become logged in as the manager and lose their administrator session since the new the token contains the manager information. Therefore, the administrator must ignore the returned token and continue using their own authentication token.

5. Why is the first-admin endpoint treated as a bootstrap operation?
The first administrator must exist before anyone can manage the system. The bootstrap endpoint allows the first administrator account to be created once for the first time. After an administrator exists, the endpoint is disabled so that attackers cannot create additional administrator accounts through a public endpoint.

6. What information can a user read from a JWT stored in localStorage?
A JWT stored in localStorage or browser cookie is not encrypted, so anyone with access to the browser can decode it. The user can read information stored in the payload, such as:
User ID
Email address
Roles
Organisation IDs
Token expiration time
However, they cannot modify these values without the JWT signature being modified.

7. How could an XSS vulnerability expose a token stored in localStorage?
If an attacker successfully injects malicious JavaScript into the application through an XSS attack, that code script can read the JWT stored in localStorage. The attacker could then send the token to another server and use it to impersonate the authenticated user until the token expires.

8. How does the CSP from Activity 06 reduce this risk?
The Content Security Policy(CSP) restricts where scripts and resources can be loaded from. By preventing untrusted JavaScript from executing, the CSP reduce XSS attacks from occurring.

9. Why are refreshed tokens returned after organisation roles change?
When a user creates or joins an organisation, their roles change. The JWT issued when they logged in still contains the old role information. Returning a refreshed token updates the JWT with the user's new roles, allowing the frontend to immediately display the correct dashboard and permissions without requiring the user to log out and log back in.

## Rate Limit
Rate limiting is a technique used to restrict how many requests a client can make to an API within a certain time frame. It is very important for authentication endpoints because without it, attackers can repeatedly to send request to the api in an attempt to crack user account passwords or create a large number of accounts using automated scripts. A per-IP limit restricts requests based on the clients IP address and a per-identifier limits requests based on the clients unique email address. When these security systems are implemented together, they are more secure. Reverse proxies and load balancers may also affect these security systems from working effectively, that is why Express needs to be configured correctly with Trust proxy. A safe request limit should be set to protect the api while also preventing legitimate users from being blocked.

## Docker
Docker is a containerisation software tool that packages an application together with its dependencies so that it can run across different environments. Docker Compose allows multiple related containers, such as a frontend and backend to be setup and started together using a single YAML file. Docker is useful for developers because it reduces environment differences and makes applications easier to deploy and run. Container building and deployment can also be automated through CI/CD pipelines. A Node.js API can be Dockerised by creating a Dockerfile that explains the Node environment, installs the applications dependencies, copies the application files, ensures the required port is visible, and starts the application. For PulseVote, Docker Compose will eventually allow the React frontend and Node.js backend to be built and run together as one application.
## Application testing
Linting is the process of analyzing source code automatically to identify errors and bad practises before the application can run. Unit tests and automated tests that check individual parts of an application to ensure that its function behaves as expected. Both are important because limiting helps maintain consistent and reliable code while unit tests help detect the location of bugs in parts of the systems source code when changes are made. These processes are automated using automated tools such as ESLint and Jest with supertest for Node.js APIs.

A React application is built before production deployment because Vite converts the source code into optimised static files that can be used efficiently. A multi-stage Docker build allows Node.js to build the React application while a smaller Nginx image is used only to serve the finished files. Nginx is suitable because the production React application consists mainly of static HTML, JavaScript, CSS files. Files such as node_modules, .env, SSL certificates, and development build output should be excluded from the Docker build context because they are not needed or may contain sensitive information. Vite variables beginning with VITE_ are embedded into the frontend during the build, whereas normal Node environment variables can be read by a Node application while it is running. Nginx's try_files configuration also allows React Router routes such as /dashboard to return index.html instead of producing a 404.

## GitHub Actions CI

Continuous Integration (CI) is the practice of automatically checking code changes whenever developers push updates or open pull requests so that problems can be detected early. GitHub Actions is GitHub’s automation platform, where a workflow contains one or more jobs and each job is made up of individual steps that run commands or reusable actions. A `push` trigger runs when code is pushed to a branch, while a `pull_request` trigger runs when changes are proposed for merging into a branch. In CI, `npm ci` is preferred over `npm install` because it installs dependencies exactly from `package-lock.json`, making builds more predictable and repeatable. Newman is the command-line runner for Postman collections, which allows the same API tests used manually in Postman to run automatically in the pipeline. Secrets such as passwords, MongoDB connection strings, and JWT secrets should be stored in GitHub Secrets, and integration tests should start from a known database state so each run is repeatable and not affected by old data.

Static code analysis examines source code without running it, looking for reliability, security, and maintainability problems before they reach production. SonarQube Cloud is a cloud-based code-quality and security platform that can identify issues such as bugs, vulnerabilities, code smells, duplication, and insufficient test coverage. A Quality Gate is a set of conditions that decides whether the analysed code meets the required quality standard, and it can fail the CI pipeline when those conditions are not met. Running SonarQube in CI is more useful than checking its dashboard manually because every pushed change is analysed automatically and poor-quality code can be stopped before later pipeline stages or deployment. Jest coverage gives SonarQube additional information about which parts of the backend are exercised by tests, helping identify important untested areas. GitHub Actions secrets are intended for sensitive values such as tokens and passwords, whereas variables are for reusable non-sensitive configuration values and are not masked by default.
