1. Why is hiding a React button not sufficient for RBAC?
Hiding a button in React only prevents users from viewing it on the interface. A malicious user can still send HTTP requests directly to the backend using online tools like Postman or by modifying the browser. To stop this the backend must verify the user's role and permissions before allowing any protected action.

2. Why does decoding a token not verify its authenticity?
Decoding a JWT simply reads information like the users email and roles, it does not prove the tokens authenticity like if the token was generated by the server or that it hasn't been modified. The Authenticity is only proven when the backend check the JWT signature using the secret key. Jwt (user token) + (server math formula) Secret key (JWT_SECRET) = JWT Signature.

3. Why must the backend check the organisation as well as the role name?
A user may have different roles in different organisations. For example, a person could be a manager in one organisation and a normal user in another. If the backend only checked the role name, a normal user could incorrectly manage polls belonging to another organisation. By checking both the role and the organisation ID, the backend ensures that users can only perform actions that they were given permission to.

4. Why must the administrator ignore the token returned when creating a manager?
When an administrator creates a manager account, the backend returns a JWT for the newly created manager. If the administrator saved this token, and they used this token then they would immediately become logged in as the manager and lose their administrator session since the new the token contains the manager information. Therefore, the administrator must ignore the returned token and continue using their own authentication token.

5. Why is the first-admin endpoint treated as a bootstrap operation?
The first administrator must exist before anyone can manage the system. The bootstrap endpoint allows the first administrator account to be created once for the first time. After an administrator exists, the endpoint is disabled so that attackers cannot create additional administrator accounts through a public endpoint.

6. What information can a user read from a JWT stored in localStorage?
A JWT stored in localStorage or browser cookie is not encrypted, so anyone with access to the browser can decode it. The user can read information stored in the payload, such as:
User ID
Email address
Roles
Organisation IDs
Token expiration time
However, they cannot modify these values without the JWT signature being modified.

7. How could an XSS vulnerability expose a token stored in localStorage?
If an attacker successfully injects malicious JavaScript into the application through an XSS attack, that code script can read the JWT stored in localStorage. The attacker could then send the token to another server and use it to impersonate the authenticated user until the token expires.

8. How does the CSP from Activity 06 reduce this risk?
The Content Security Policy(CSP) restricts where scripts and resources can be loaded from. By preventing untrusted JavaScript from executing, the CSP reduce XSS attacks from occurring.

9. Why are refreshed tokens returned after organisation roles change?
When a user creates or joins an organisation, their roles change. The JWT issued when they logged in still contains the old role information. Returning a refreshed token updates the JWT with the user's new roles, allowing the frontend to immediately display the correct dashboard and permissions without requiring the user to log out and log back in.

## Rate Limit
Rate limiting is a technique used to restrict how many requests a client can make to an API within a certain time frame. It is very important for authentication endpoints because without it, attackers can repeatedly to send request to the api in an attempt to crack user account passwords or create a large number of accounts using automated scripts. A per-IP limit restricts requests based on the clients IP address and a per-identifier limits requests based on the clients unique email address. When these security systems are implemented together, they are more secure. Reverse proxies and load balancers may also affect these security systems from working effectively, that is why Express needs to be configured correctly with Trust proxy. A safe request limit should be set to protect the api while also preventing legitimate users from being blocked.
